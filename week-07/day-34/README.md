# День 34 — файловый помощник iRon

## Задание

Скопированный TUI-агент недели 04 получает узкий, разрешённый набор файловых MCP-инструментов для изучения и подготовки документации проекта iRon. Агент может исследовать репозиторий и предложить изменения Markdown, но не вносит их в рабочую копию без локального просмотра diff и отдельного подтверждения пользователя.

Сценарий дня работает с форком [VaSeWS/iRon_fork](https://github.com/VaSeWS/iRon_fork), закреплённым на revision `cb76b89633554e1dd7f288087054f30b00bd9a55`. Задача — изучить Delta overlay: проследить реализацию динамического масштаба, места вызова и тесты с точными ссылками на файлы и строки; затем подготовить новый Markdown-гайд и добавить ссылку на него в существующую архитектурную документацию. Перед изменениями агент должен прочитать текущие документы и сделать гайд дополнением к архитектурной заметке, которая уже описывает масштабирование. Изменения исходников C++ не входят в сценарий.

## Архитектура

`week-07/day-34` — отдельный `package main`, скопированный из `week-04/agent`; это не общий framework, и прежний агент и задачи предыдущих недель не изменяются. День 34 добавляет проектный workspace и соединяет его с tool-calling циклом агента:

1. TUI или headless-режим передаёт задачу обычному агенту.
2. Агент получает четыре project MCP tools и может вызывать их по мере необходимости. События вызовов накапливаются в течение turn и показываются журналом после его завершения, а не транслируются по мере вызова.
3. `project_list_files`, `project_read_file` и `project_search_files` читают безопасное представление проекта, включая текущие staged-изменения.
4. `project_write_file` подготавливает полное содержимое разрешённого Markdown-файла в памяти. Повторная запись заменяет предыдущую staged-версию; возврат исходного содержимого убирает pending change.
5. Пользователь проверяет `/diff` и явно подтверждает запись через `/apply`, затем `/confirm`. `/reject` отбрасывает все staged-изменения. Модель не получает инструмента применения или отклонения.

Те же четыре инструмента можно независимо подключить как stdio MCP server. Ответы MCP включают структурированный объект и JSON-текст. Проектный MCP не запускает модель и не применяет staged-файлы.

## Быстрый старт

Нужны Go версии `1.25.5` (версия модуля) и ключ DeepSeek. По умолчанию используется провайдер DeepSeek (`deepseek-flash`, OpenAI-compatible endpoint `https://api.deepseek.com/chat/completions`); ключ берётся только из `DEEPSEEK_API_KEY` через окружение, не из файла конфигурации. Не вставляйте ключ в командную историю, аргументы команд, README или TUI. Для удалённых запросов перед отправкой проверяйте, какие разрешённые файлы могут попасть в контекст модели.

```sh
export DEEPSEEK_API_KEY='…'  # задайте локально; никогда не публикуйте значение

# Из корня ai-advent-challenge создайте отдельную свежую копию iRon на точном revision.
IRON_ROOT="$(bash ./week-07/day-34/video/prepare.sh)"
printf 'Pinned iRon checkout: %s\n' "$IRON_ROOT"

# Запустить TUI, указав корень iRon. DB по умолчанию: week-07/day-34/agent.db.
go run ./week-07/day-34 -root "$IRON_ROOT"
```

Для отдельного состояния агента задайте `-db PATH`; для headless-выполнения одной задачи добавьте `-task 'Текст задачи'`. Headless-режим использует тот же агент и реальные вызовы API/tools, печатает события вызванных инструментов и diff с буквальным заголовком `Staged diff (not applied):`; он не применяет изменения. После завершения headless-процесса staged-состояние теряется, поэтому для локального просмотра и подтверждения используйте TUI. Для объёмной документации задайте `-max-tokens 8192`; `-tool-rounds` по умолчанию равен 24, допустим диапазон — 1–100.
В одном turn файловые project tools могут вызываться повторно по мере исследования; прочие подключённые MCP tools допускаются не более одного раза каждый. `-tool-rounds` ограничивает продолжение tool-calling, а не число файловых операций внутри одного round.

В профиле дня 34 для DeepSeek заданы лимиты до 8192 токенов основного ответа и до 4096 вспомогательного; `-max-tokens` и `-aux-max-tokens` позволяют задать другие значения. Извлечение памяти использует встроенный режим JSON-object в API DeepSeek и проверяет полученный объект по прежним строгим правилам. Ошибка файлового инструмента остаётся видимым failed-событием и передаётся модели как JSON с полем `error`; дальнейшее действие выбирает модель в пределах того же лимита rounds. Автоматического повтора нет, сетевых retry/backoff нет. Ошибки провайдера, памяти и сторонних MCP-инструментов завершают запрос явно.

### Локальные команды TUI

| Команда | Действие |
| --- | --- |
| `/diff` | Показать текущие staged-изменения. |
| `/apply` | Повторно показать diff и запросить явное подтверждение командой `/confirm`; не записывает файлы самостоятельно. |
| `/confirm` | Применить без изменения только diff, показанный последним `/apply`; если staged-состав изменился, команда требует проверить diff заново. |
| `/reject` | Отбросить staged-изменения без записи. |

Эти команды доступны только локальному пользователю в TUI; агентская модель не может вызвать их как MCP tools. Если staged-изменения ожидают решения, `Ctrl+C` и `/quit` не завершают TUI: выполните `/reject` либо завершите применение через `/apply` и `/confirm`. Завершение процесса без применения теряет pending-изменения.

### Отдельный MCP server

Из корня модуля запустите сервер как stdio subprocess, передав ему абсолютный или относительный корень проекта:

```sh
go run ./week-07/day-34 mcp -root "$IRON_ROOT"
```

Команда ожидает JSON-RPC/MCP на stdin и пишет stdio-протокол в stdout. Доступны ровно четыре инструмента:

| Tool | Аргументы |
| --- | --- |
| `project_list_files` | `path` — необязательный относительный путь. |
| `project_read_file` | `path` — относительный путь; `start_line` — необязательная первая строка с нумерацией от 1, `end_line` — необязательная последняя строка включительно. |
| `project_search_files` | `query` — текстовый запрос; `path` — необязательный относительный путь. |
| `project_write_file` | `path` — относительный путь; `content` — полное содержимое файла. |

`project_write_file` только обновляет staged overlay. MCP server не предоставляет модели `/apply`, `/confirm` или `/reject`; `Apply` и `Reject` — локальные операции workspace API.

## Границы доступа и безопасность

- Пути должны оставаться внутри корня проекта: абсолютные пути, `..`, NUL и symlink-компоненты внутри дерева отклоняются. Сам выбранный корень не может быть symlink; его symlink-предки разрешаются до канонического пути. Файловые операции выполняются относительно открытого корня.
- Из list/read/search/write исключаются `.git`, `.env*`, credential/key-файлы и каталоги сторонних зависимостей/артефактов сборки согласно общей политике workspace. Фильтр имён — не детектор секретов: секрет в обычном Markdown может быть прочитан и отправлен провайдеру.
- Записывать можно только корневой `README.md` и Markdown-файлы внутри `docs/` или `memory-bank/`; похожие имена каталогов с префиксом не расширяют разрешение. Новые файлы допустимы только в этой области.
- Разрешены только обычные UTF-8 файлы без NUL. Для замены существующего файла требуется полное исходное чтение; усечённый/частичный ответ не разрешает замену. Для больших файлов используйте диапазоны строк для чтения; если полное чтение превышает лимит ответа, такой файл нельзя безопасно заменить целиком этим инструментом.
- Ограничения: файл и staged-файл — до 1 MiB; весь overlay — до 8 MiB и 100 файлов; list/search/read — до 64 KiB с явным признаком усечения; поиск возвращает максимум 100 совпадений; обход ограничен 10 000 entries.
- Поиск — буквальный текстовый, а не семантический: он не гарантирует полноту анализа символов, ссылок, вызовов или поведения программы. При рекурсивном поиске файлы на диске с невалидным UTF-8, NUL или размером свыше 1 MiB пропускаются; число таких исключений указано в `skipped_files` (оно не означает усечение результатов). Списки файлов намеренно исключают некоторые каталоги (например, `third_party` и артефакты), поэтому отсутствие пути в выдаче не доказывает его отсутствие на диске. Ответ `project_read_file` не содержит пронумерованных строк; для точных номеров строк используйте результаты поиска и проверьте их по содержимому. Проверяйте цитаты и семантические выводы модели по исходникам: модель может ошибиться, в том числе назвать неверные смещения строк. Для расследования проверяйте реализации, call sites, тесты и документацию инструментами чтения.
- Перед записью workspace предварительно сверяет все исходные файлы с диском: при staging существующего файла сохраняется исходное содержимое, для нового — факт отсутствия. Появление нового файла или изменение исходного до Apply приводит к конфликту до первой записи; pending изменения остаются доступны для diff/отклонения. Файлы подготавливаются временно в целевом каталоге, режим существующего файла сохраняется, новые файлы неисполняемые; существующие hardlink-файлы не перезаписываются in-place. Перед каждым rename выполняется повторная проверка. При частичной ошибке сообщение указывает уже применённые пути; они удаляются из pending, остальные остаются staged.
- Применение не является транзакцией на уровне всей файловой системы. Сверки размера/mtime и `Lstat` не атомарны с записью/rename; `os.Root` не допускает выхода из корня, но workspace не защищает от конкурентной враждебной мутации файлов тем же пользователем и не предоставляет compare-and-swap. Внешние редакторы не синхронизируются с mutex приложения.
- Staged-состояние in-memory: аварийное завершение или закрытие без применения теряет pending-изменения. Сохраняйте diff отдельно, если он нужен после завершения процесса.

## Воспроизведение iRon сценария

`video/prepare.sh` каждый раз создаёт отдельную копию репозитория iRon на закреплённом SHA. Без аргумента скрипт использует новый временный каталог; с аргументом принимает только ещё не существующий путь. Скрипт не удаляет существующие каталоги и не использует `git reset --hard`. Не редактируйте исходную рабочую копию iRon.

Для TUI-демо нужны Git, Go `1.25.5`, `tmux` и экспортированный `DEEPSEEK_API_KEY`. Скрипт запускает собственный foreground tmux server; пользовательские tmux-сессии он не останавливает. Сценарий выполняет два goal-запроса к DeepSeek и файловым инструментам. Журнал вызовов появляется после завершения каждого turn, а не во время вызовов. Затем скрипт показывает diff, выполняет `/apply` и подтверждает изменения; отдельный запрос перечитывает сохранённые Markdown-файлы. Сценарий использует реальные ответы модели; имена и содержание созданных документов могут отличаться при повторном запуске.

```sh
bash ./week-07/day-34/video/demo.sh
```
