# День 33 — помощник поддержки iRon

Автономный локальный Go-сервис: встроенный адаптивный интерфейс на русском языке, лексический поиск BM25 по документации и контекст синтетической CRM через MCP. Данные обращений созданы для демонстрации; это не база реальных пользователей.

## Запуск

Из корня репозитория:

```sh
export DEEPSEEK_API_KEY=your_key
go run ./week-07/day-33
```

Откройте <http://127.0.0.1:8033>. Ключ читается только из переменной окружения `DEEPSEEK_API_KEY`: приложение не загружает `.env`, не сохраняет ключ, не повторяет запросы и не переключается на другого провайдера. Без ключа доступны интерфейс и локальные CRM-маршруты; запрос чата завершится безопасной ошибкой.

Необязательные параметры:

```sh
go run ./week-07/day-33 -addr 127.0.0.1:8033 -model deepseek-flash
```

`-addr` задаёт адрес HTTP-сервера (по умолчанию только loopback); `-model` выбирает модель DeepSeek (по умолчанию `deepseek-flash`). Сервис отправляет обычный, не потоковый запрос Chat Completions на `https://api.deepseek.com/chat/completions`, запрашивает JSON и отключает thinking, чтобы получать краткий структурированный ответ. Браузер получает NDJSON-события: этапы появляются только при фактическом запуске MCP, поиска и модели.

## Архитектура и API

- `main.go` встраивает `web/*`, `data/crm.json` и `corpus/*`; во время работы соседние каталоги не нужны.
- `support.go` читает манифест происхождения материалов, разбивает текст на фрагменты и ранжирует их BM25 с токенизацией кириллицы и английского. Источники содержат точные диапазоны строк встроенного локального снимка. Идентификаторы цитат детерминированы, а ссылки модели принимаются только из списка найденных фрагментов.
- `mcp.go` реализует JSON-RPC MCP stdio: `initialize`, `tools/list`, `tools/call`. На каждый чат HTTP-сервис запускает отдельный процесс этой же программы с привязкой к выбранному пользователю CRM. `get_user` возвращает только привязанную личность, `get_ticket` запрещает доступ к обращению другого пользователя.
- История хранится только в памяти процесса, раздельно по идентификатору браузерной сессии, пользователю и обращению; она ограничена и исчезает при остановке сервиса. Одновременный запрос для одного такого ключа отклоняется.

Маршруты HTTP:

- `GET /api/bootstrap` → `{users, model, synthetic}`.
- `GET /api/tickets?user_id=...` → `{tickets}` выбранного пользователя.
- `GET /api/ticket?user_id=...&ticket_id=...` → `{user, ticket, messages}`; необходим заголовок `X-Session-ID`.
- `POST /api/chat` принимает `{user_id, ticket_id, message}` и заголовок `X-Session-ID`; ответ — NDJSON-события `stage`, затем `answer` либо `error`.

Браузер создаёт случайный `X-Session-ID` и хранит его в `sessionStorage`. Это только разделитель истории, а не аутентификация. Выбор демонстрационного пользователя также не является производственной аутентификацией. Изменяющие запросы принимаются только от loopback-клиента с точным loopback `Origin`, совпадающим с `Host`. Оставляйте привязку сервера на loopback; не выставляйте демонстрацию в сеть и не считайте синтетические обращения данными клиентов. Ошибки провайдера и секреты не передаются браузеру.

## Происхождение, приватность и ограничения

`corpus/manifest.json` фиксирует источник материалов: `VaSeWS/iRon_fork`, выбранный снимок `iRon-ai-review` с SHA `cb76b89633554e1dd7f288087054f30b00bd9a55`, пути `README.md` и `LICENSE` и примечание о выборе. Это выбранный источник документации, а не утверждение о самой новой ревизии. Локальный корпус включает только отмеченные в манифесте диапазоны README; FAQ содержит выводы, подтверждаемые этими материалами. Цитаты и диапазоны строк относятся к встроенному локальному снимку, ссылки ведут на закреплённую upstream-ревизию. CRM и обращения синтетические; сервис не индексирует исходный код, не проверяет его поведение и не подключается к реальным учетным записям iRon.

При отправке вопроса сервис передаёт DeepSeek на `api.deepseek.com` текст вопроса, выбранные локальным поиском фрагменты документации, контекст выбранного синтетического пользователя и обращения (включая его описание, конфигурацию, проверки и начальную историю), наблюдения MCP и ограниченную предыдущую переписку. Хранилище оставляет не более 24 сообщений для сочетания браузерной сессии, пользователя и обращения. Не отправляйте реальные персональные данные, секреты или содержимое реальных обращений.

В приложении нет проверки реальной аутентификации: выбор демонстрационного пользователя — не вход в учетную запись. Сессии и переписка хранятся только в памяти процесса и теряются при остановке или перезапуске сервиса. Оставляйте сервер привязанным к loopback и не выставляйте демонстрацию в сеть. Фактический запуск iRon в Windows не выполнялся; указание Windows в синтетическом профиле не является свидетельством совместимости.

## Статус проверок

На итоговой версии прошли `go test ./...` (11 пакетов успешно, 6 без тестов), `go build ./...`, `go test -race ./week-07/day-33`, `go vet ./week-07/day-33` и синтаксическая проверка обоих JavaScript-файлов. Live smoke-проверка подтвердила ответы с источниками для `ghost: off`, запрос недостающей конфигурации при неизвестном `ghost`, продолжение переписки и приоритет исправления пользователя над устаревшими данными CRM. Также проверены отказ в доступе к чужому обращению (HTTP 404), ошибки MCP и отсутствие ключа, новая сессия без прежней истории и изоляция черновиков. В браузере проверены ширины 1440, 1600, 1024 и 833 px: при раскрытых источниках высота документа равна высоте окна; на ширинах 832, 825 и 390 px горизонтального переполнения нет. Запуск iRon в Windows и реальная аутентификация не проверялись.

Видео записано с реальными ответами DeepSeek и визуально проверено; оно опубликовано через локальный MCP Яндекс Диска: [день 33 — поддержка iRon](https://yadi.sk/d/MTFZQbZ1T2Py_A). H.264, 1600×1100, 30 fps, 94,67 с, без звука. В записи показаны ответ при `ghost: off`, источники и наблюдения MCP, уточнение при неизвестной конфигурации и продолжение диалога. Сценарий и процедура записи описаны в [`video/README.md`](video/README.md).
