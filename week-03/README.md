# Week 03 — Memory Agent

`week-03` — самостоятельная программа `package main` в корневом Go-модуле. Она не импортирует `week-02` и хранит своё состояние в указанной SQLite-базе. Агент сохраняет raw-диалог, рабочее состояние активной задачи, выбранный профиль, долговременные решения и знания, а также активные инварианты и журнал переходов задачи.

Новые memory layers не заменяют режимы контекста `full`, `summary`, `sliding`, `facts` и `branching`: те по-прежнему определяют, какая часть истории активной ветки попадает в запрос.

## Запуск с временной базой

Нужны Go 1.25.5, интерактивный терминал и непустая переменная окружения ключа выбранного провайдера: для Groq — `GROQ_API_KEY`, для DeepSeek — `DEEPSEEK_API_KEY`. Программа читает ключ только из окружения; не помещайте его в командную историю, исходный код или базу данных.

Создайте временный каталог и сохраните путь к базе в переменной: этот же путь используйте при каждом повторном запуске сценария.

```sh
tmp_dir="$(mktemp -d)"
db="$tmp_dir/week-03.db"
cd week-03
go run . -db "$db" -provider groq
```

Для DeepSeek замените `-provider groq` на `-provider deepseek`; перед этим задайте `DEEPSEEK_API_KEY`. Для запуска с Groq заранее задайте `GROQ_API_KEY`. Допустимы только провайдеры `groq` и `deepseek`. Если соответствующий ключ отсутствует, программа завершится до открытия TUI.

Без `-db` программа использует `agent.db` в текущем каталоге. `/quit` или `Ctrl+C` корректно закрывают базу. Удалить временное состояние после демонстрации можно вне программы:

```sh
rm -rf "$tmp_dir"
```

## Модель памяти и следующий prompt

После успешного пользовательского turn агент выполняет отдельное structured memory-извлечение. Допустимые обновления сохраняются атомарно вместе с raw user/assistant сообщениями и учётом вызовов. Невалидный либо неоднозначный результат извлечения не оставляет частично записанного turn.

Слои изолированы:

- **raw dialogue** — сообщения активной ветки;
- **working task memory** — цель, план, фаза, текущий шаг, ожидаемое действие и признак паузы активной задачи;
- **long-term memory** — выбранный профиль и записи `decision`/`knowledge`, принадлежащие активному профилю либо задаче;
- **invariants** — отдельные активные структурированные требования задачи;
- **task history** — неизменяемые записи успешных переходов.

Основной запрос строится в фиксированном порядке. Каждый пункт до истории — отдельное `system`-сообщение:

1. базовое системное правило;
2. активные invariants;
3. активный профиль;
4. долговременные решения и знания текущего scope;
5. снимок активной задачи;
6. выбранная стратегия контекста (`summary`, `facts`, raw lineage и т. п.);
7. текущий ввод пользователя.

Следовательно, профиль меняет язык, стиль и формат ответа, но не может отменить invariant, lifecycle guard или базовое системное правило. Базовое правило требует отказа и безопасной альтернативы при конфликте invariants; task system block содержит допустимое событие текущей фазы и подсказку для паузы. `/inspect` не вызывает и не сохраняет rail: для запрещённого кандидата он показывает совпавший invariant и помечает assembled messages как `hypothetical main request if allowed`, а не как отправляемый запрос.

## Команды

Все команды вводятся в поле сообщения TUI. Разделитель `|` удобен для значений с пробелами; угловые скобки обозначают значение, которое нужно подставить.

### Профили

| Команда | Действие |
| --- | --- |
| `/profile create <name> \| <language> \| <response-style> \| <response-format> \| <constraints>` | Создать именованный профиль. Первые четыре поля обязательны; ограничения могут быть пустыми. |
| `/profile select <profile-id>` | Выбрать уже сохранённый профиль. |
| `/profile show` | Показать все профили и отметить активный. |

Выбор активного профиля сохраняется в базе и восстанавливается после перезапуска. Автоматическое извлечение может обновлять только поля выбранного профиля, но не переключает профиль.

### Активная задача и lifecycle

| Команда | Действие |
| --- | --- |
| `/task create <goal> \| <plan> \| <current-step> \| <expected-action>` | Создать активную задачу ветки, если её ещё нет; начальная фаза — `planning`. |
| `/task show` | Показать сохранённый снимок активной задачи. |
| `/task update <plan\|step\|action> <value>` | Изменить план, текущий шаг или ожидаемое действие. |
| `/task pause` / `/task resume` | Установить либо снять паузу без изменения фазы, шага и ожидаемого действия. |
| `/task transition <approve_plan\|submit_result\|validation_passed\|validation_failed>` | Выполнить проверяемый переход фазы. |
| `/task history` | Показать хронологический журнал успешных переходов. |

Фазы только такие: `planning`, `execution`, `validation`, `done`. Разрешены только следующие события:

| Событие | Переход |
| --- | --- |
| `approve_plan` | `planning` → `execution` |
| `submit_result` | `execution` → `validation` |
| `validation_passed` | `validation` → `done` |
| `validation_failed` | `validation` → `execution` |

Пауза блокирует переходы. Недопустимый переход возвращает ошибку, сохраняет фазу и не добавляет запись в `/task history`.

### Долгосрочная память

| Команда | Действие |
| --- | --- |
| `/memory add <profile\|task> \| <decision\|knowledge> \| <key> \| <value>` | Атомарно сохранить запись только в активном profile или активной task текущей ветки. |
| `/memory list` | Показать записи текущих активных profile и task в детерминированном порядке. |

`/memory add` не принимает owner ID и не может записать в неактивный scope. При активной задаче invariants защищают и profile-, и task-scoped структурированные решения.

### Инварианты

| Команда | Действие |
| --- | --- |
| `/invariant add <category> \| <key> \| <required-value> \| <rule> \| <source> [\| <forbidden-terms>]` | Добавить active requirement текущей задачи; шестое поле необязательно. |
| `/invariant list` | Показать инварианты активной задачи, включая forbidden terms. |
| `/invariant deactivate <invariant-id>` | Деактивировать инвариант текущей задачи. |

Шестое поле — список запрещённых подстрок через запятую: при сохранении каждая часть trim/lowercase, пустые части и дубликаты без учёта регистра отклоняются. Пустое или отсутствующее поле выключает input rail. Запятые разделяют термины, а совпадение — literal substring без границ слов или regexp. До overflow и любых main/auxiliary LLM-вызовов rail один раз сопоставляет raw user input с active invariant case-insensitive Unicode substring. Совпадение сохраняет user turn и детерминированный русский refusal, не создаёт API, summary, facts или memory обновлений; deactivated invariant не участвует.

### Инспекция prompt

```text
/inspect <candidate-message>
```

Команда не отправляет запрос провайдеру. Она показывает raw dialogue, рабочую задачу, профиль, долгосрочную память и invariants, а затем точные пронумерованные сообщения, которые программа отправила бы для `<candidate-message>`.

Остальные команды контекстного агента остаются доступны: `/new`, `/chats`, `/use`, `/mode`, `/window`, `/checkpoint`, `/fork`, `/branches`, `/switch`, `/facts`, `/stats [all]`, `/help` и `/quit`.

## Ручные сценарии

Во всех сценариях сначала выполните запуск из раздела выше. Сценарии независимы: для каждого создайте новый `tmp_dir` и `db`, если только шаг явно не требует перезапуска с тем же `"$db"`. Команды после этого вводятся в TUI.

### 1. Persistence и автоматическая память

1. Создайте и выберите профиль, который extractor сможет обновить:

   ```text
   /profile create Предпочтение | English | concise | text |
   /profile select 1
   ```

2. Введите сообщение, содержащее устойчивое предпочтение: `Отвечай по-русски, краткими маркированными пунктами.`
3. После успешного ответа введите `/inspect Какой формат ответа ты применишь?`. В слоях и системных сообщениях проверьте raw dialogue и обновлённые поля активного профиля.
4. Введите `/quit`, затем снова запустите `go run . -db "$db" -provider groq`.
5. Повторите `/profile show` и `/inspect Какой формат ответа ты применишь?`. Сохранённый профиль, raw dialogue и их влияние на следующий prompt должны остаться доступными.

Извлечение преднамеренно сохраняет только устойчивые, разрешённые данные. Подтверждение конкретных слоёв даёт `/inspect`.

### 2. Два профиля и восстановление выбранного

```text
/profile create Краткий | Russian | concise | bullets | Без эмодзи
/profile create Подробный | Russian | detailed | text | Приводи источники
/profile show
/profile select 2
/inspect Объясни состояние задачи
/quit
```

После перезапуска с тем же `"$db"` выполните:

```text
/profile show
/inspect Объясни состояние задачи
```

У профиля `Подробный` должна остаться отметка активного, а его поля должны быть в profile system block. Выберите `/profile select 1` и снова выполните `/inspect`, чтобы сравнить контекст без повторного создания профиля.

### 3. Пауза и resume без потери снимка

```text
/task create Обновить схему | Описать миграцию | Согласовать план | Запросить approve_plan
/task update plan Описать v1-to-v2 миграцию
/task update step Дождаться согласования
/task update action Подтвердить план
/task pause
/task show
/quit
```

После перезапуска:

```text
/task show
/task resume
/task show
```

До `resume` снимок должен иметь `paused: true`; после него — `paused: false`. Фаза `planning`, план, текущий шаг и ожидаемое действие должны остаться теми же.

### 4. Конфликт с invariant без изменения задачи

В новой временной базе создайте задачу и закрепите её план:

```text
/task create Выбрать хранилище | Использовать SQLite | Зафиксировать решение | Не менять storage
/invariant add task | plan | Использовать SQLite | План обязан сохранять SQLite. | architecture
/invariant add decision | storage | SQLite | Решение о хранилище должно сохранять SQLite. | architecture
/task show
/task update plan Перейти на PostgreSQL
/task show
/invariant list
```

`/task update` должен вернуть `invariant conflict` с правилом и безопасным действием. Второй `/task show` обязан по-прежнему содержать план `Использовать SQLite`. `/inspect Предложи другое хранилище` показывает оба active invariants раньше profile и текущего сообщения. Если в следующем turn auxiliary extractor предложит структурированное решение `decision.storage=PostgreSQL`, второй invariant с точно теми же `category` и `key` отклонит обновление без записи конфликтующего решения.


### 5. Input rail и конфликт без вызова LLM

```text
/task create Защитить ввод | Не обрабатывать запрещённый термин | Проверить rail | Отказать безопасно
/invariant add input | terms | safe | Не обрабатывать запрещённый термин. | policy | секрет
/inspect Покажи СЕКРЕТ
Покажи секрет
/invariant deactivate 1
Покажи секрет
```

`/inspect` должен сообщить matched invariant rail и показать только hypothetical request. Второе сообщение сохраняется вместе с русским refusal без API rows, summary/facts/memory updates. После deactivation тот же ввод больше не блокируется и идёт обычным путём.

### 6. Недопустимый и допустимый lifecycle

В новой временной базе создайте задачу в `planning`, затем выполните:

```text
/task create Проверить lifecycle | Пройти фазы | Утвердить план | Вызвать approve_plan
```

```text
/task history
/task transition submit_result
/task show
/task history
```

Переход `planning` → `validation` отклоняется: фаза остаётся `planning`, а журнал остаётся пустым. Затем пройдите разрешённый путь:

```text
/task transition approve_plan
/task transition submit_result
/task transition validation_passed
/task show
/task history
```

Ожидаемая фаза — `done`; `/task history` содержит три записи в том же порядке: `approve_plan`, `submit_result`, `validation_passed`.

## Миграция v1/v2 → v3 и rollback

`week-03` открывает новую базу или SQLite-базу схемы v1/v2 и атомарно переводит её в schema version 3. v3 добавляет к `invariants` столбец `forbidden TEXT NOT NULL DEFAULT ''`; уже v3-база открывается без изменения, а база v4 и новее отклоняется без изменения.

Не запускайте миграцию над единственной копией v1- или v2-базы. Сначала создайте резервную копию и передайте `week-03` путь именно к копии:

```sh
cp /путь/к/старой-v1.db "$tmp_dir/week-02-v1-backup.db"
cp "$tmp_dir/week-02-v1-backup.db" "$tmp_dir/week-03-upgrade.db"
cd week-03
go run . -db "$tmp_dir/week-03-upgrade.db" -provider groq
```

Чтобы откатиться, закройте программу и снова используйте нетронутую старую копию; не открывайте уже мигрированную v3-базу старой программой.
