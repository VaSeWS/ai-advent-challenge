# День 18 — периодический MCP-планировщик повторения

Самостоятельный Go MCP-сервер на `github.com/modelcontextprotocol/go-sdk/mcp`. Пока процесс запущен, он регулярно читает Markdown-файлы Obsidian в режиме read-only, выбирает записи с корректным `sr-due: YYYY-MM-DD`, сроком сегодня или раньше, и при необходимости фильтрует их по hashtag (`#Go`, `#Python`, `#Architectural` и т. п.). Записи без даты и с невозможной датой пропускаются. Файлы Vault никогда не изменяются.

Расписание и история запусков сохраняются в JSON (по умолчанию `week-04/day-18/state.json`) и загружаются при следующем старте. По умолчанию Vault: `~/Documents/Obsidian Vault/Interviews prep/Questions`; переменная `OBSIDIAN_VAULT` или флаг `-vault` задаёт другой каталог. `REVIEW_SCHEDULER_STATE` или флаг `-state` задаёт другой JSON-файл. Не храните в state-файле содержимое заметок: он содержит только сохранённые результаты поиска (названия, теги, даты и относительные пути).

## Запуск и демонстрация

Откройте два терминала из корня репозитория.

**Терминал 1 — запустите сервер:**

```sh
go run ./week-04/day-18 -listen 127.0.0.1:8080
```

**Терминал 2 — создайте расписание `#Go` с интервалом 2 секунды:**

```sh
go run ./week-04/day-18 -mode schedule -listen 127.0.0.1:8080 -topic '#Go' -interval 2s
```

Оставьте сервер работать и дождитесь нескольких тиков. Затем запросите реальные агрегаты и результаты:

```sh
go run ./week-04/day-18 -mode summary -listen 127.0.0.1:8080
```

Чтобы проверить восстановление JSON-состояния, остановите сервер в первом терминале (`Ctrl-C`), снова запустите той же командой и повторите команду summary во втором терминале. `-endpoint http://127.0.0.1:8080` можно указать вместо `-listen 127.0.0.1:8080` в клиентских командах. По умолчанию клиент подключается к `http://127.0.0.1:8080`. Клиентские режимы вызывают инструменты через Go MCP SDK; клиент не обращается к Vault и не пишет файлы. Запланированные чтения Vault и JSON persistence выполняет только сервер. Для обычной работы используйте интервал подольше, например `24h`; минимальный интервал — `1s`.

Это не фоновый облачный сервис: расписания исполняются только пока серверный процесс работает. Чтобы обеспечивать непрерывную работу, пользователь должен запустить его на постоянно работающем хосте и управлять жизненным циклом процессом/службой. Во время остановки тики не выполняются; при перезапуске сохранённое расписание продолжает работу, а пропущенные интервалы не воспроизводятся задним числом.

## MCP-инструменты

- `schedule_due_questions`: `{ "topic": "#Go", "interval": "5s" }`; пустая тема сканирует все темы. Создаёт периодическое расписание и возвращает его ID и время следующего выполнения.
- `scheduler_summary`: без аргументов возвращает агрегаты и историю результатов (в том числе заголовки вопросов для демонстрации).
