# Неделя 5 — RAG-движок, оценка и чат

Эта неделя собирает локальный конвейер поиска по зафиксированному снимку вики GT: New Horizons (GT:NH): снимок корпуса → Ollama embeddings и SQLite/sqlite-vec индекс → поиск и сравнение ответов → терминальный чат с двумя изолированными линиями. Все дни используют один самостоятельный Go-пакет `week-05` (`package main` в `week-05/main.go`), запускаемый из корня как `go run ./week-05`; папки `day-21` … `day-25` содержат видео-демо, а не отдельные Go-пакеты.

## Дни 21–25

- **День 21 — корпус, чанки и индекс:** загрузка закреплённых редакций вики, разбиение текста фиксированными и структурными чанками, Ollama embeddings, fingerprint модели и подготовка SQLite-индекса.
- **День 22 — первый RAG и сравнение:** получение ответа по найденному контексту и сравнение двух линий в evaluation/TUI.
- **День 23 — фильтрация и переписывание:** отсечение retrieval-кандидатов порогом сходства и поиск с переписанным запросом.
- **День 24 — цитаты и отказ:** проверяемые цитаты из переданного контекста и явный ответ о недостаточности корпуса, когда доказательств нет.
- **День 25 — чат и память:** TUI с парными линиями, сохранением сессий, ограниченной историей и lane-local task memory.

## Требования и ключи

Нужны Go 1.25.5 и запущенный Ollama с embedding-моделью `nomic-embed-text:latest` (768 измерений). Индексация и поиск используют Ollama; генерация ответов по умолчанию идёт через Groq. Провайдер выбирается явно параметром `-provider groq|deepseek`; `-endpoint` при необходимости задаёт совместимый Chat Completions endpoint. По умолчанию Groq использует `https://api.groq.com/openai/v1/chat/completions`, DeepSeek — `https://api.deepseek.com/chat/completions`. По умолчанию DeepSeek использует `deepseek-flash` для основной и вспомогательной модели. Провайдер и endpoint сохраняются в сессии.

Ключ читается только из переменной окружения: `GROQ_API_KEY` или `DEEPSEEK_API_KEY`. `.env` — только локальная справочная запись: Go-код сам его не загружает. Можно экспортировать ключ непосредственно в текущем shell или загрузить доверенный shell-совместимый `.env`, не печатая содержимое:

```sh
export GROQ_API_KEY='ключ'
# либо для DeepSeek:
export DEEPSEEK_API_KEY='ключ'

# Альтернатива: только если .env содержит доверенные shell assignments.
set -a
. ./.env
set +a
```

Например, можно задать провайдера и endpoint явно:

```sh
go run ./week-05 chat -provider deepseek \
  -endpoint https://api.deepseek.com/chat/completions
```

Не добавляйте ключ в командную строку, скриншоты, отчёты или репозиторий; не используйте `cat .env`, `echo $GROQ_API_KEY` и подобные команды, раскрывающие значение. `.env` и `.env.local` игнорируются Git.

Groq получает запросы с режимом строгой JSON Schema. DeepSeek получает `json_object` и инструкции со схемой, после чего приложение валидирует декодированный объект локально по той же схеме; это не эквивалент серверной строгой валидации Groq. При retrieval найденный текст корпуса включается в запрос к выбранному внешнему провайдеру и отправляется ему. В частности, `-provider deepseek` передаёт DeepSeek запрос и найденные фрагменты по его Chat Completions API: это внешняя передача данных, а не локальная генерация. Не используйте данные, которые нельзя передавать выбранному провайдеру.

## 1. Снимок корпуса (день 21)

В репозитории есть снимок `corpus/gtnh-20261004.json`: 19 страниц, закреплённых за редакциями вики. Команда отчёта читает именно его и ничего не скачивает:

```sh
go run ./week-05 corpus -report week-05/corpus/gtnh-20261004.json
```

Новый снимок загружается из API вики в новый файл; `-out` не перезаписывает существующий:

```sh
go run ./week-05 corpus -out week-05/corpus/gtnh-new.json
```

Укажите другой набор страниц через `-titles 'Title One|Title Two'`. Отчёт перечисляет page/revision ID, дату редакции и получения, URL и permalink, SHA-256 нормализованного текста, разделы, предупреждения и лицензию. Снимок — не полная копия вики: изображения и их содержание, полные NEI/Quest Book рецепты и отсутствующие игровые данные не становятся доступными доказательствами. Даты редакций — не версии модпака; версии-зависимые сведения нужно проверять по permalink и отдельно сверять с нужной версией.

**Атрибуция и лицензия.** Сохранённый манифест указывает для всех 19 страниц: GT New Horizons Wiki, [CC BY-SA 4.0](https://creativecommons.org/licenses/by-sa/4.0/). Постоянные ссылки на использованные редакции находятся в [отчёте корпуса](corpus/REPORT.md) и в отчёте `corpus -report`. При повторном использовании текста сохраняйте авторство и источник, указывайте изменения и соблюдайте применимые условия ShareAlike лицензии.

## 2. Индекс и его проверка (день 21)

По умолчанию индекс использует снимок `gtnh-20261004.json`, базу `week-05/rag.db`, модель `nomic-embed-text:latest`, 768 измерений и чанки **400 слов с перекрытием 80 слов**. Fingerprint включает имя, фактический digest весов, подготовку текста и размерность; для текущего build это `nomic-embed-text:latest`, digest `0a109f422b47e3a30ba2b10eca18548e944e8a23073ee3f3e947efcf3c45e59f`, `search_document:/search_query: v1`, 768 измерений. При построении и поиске fingerprint Ollama сверяется с индексом; несовпадение не следует обходить переименованием модели или использованием старых векторов.

```sh
# Подготовить/активировать индекс из зафиксированного снимка.
go run ./week-05 index

# Только прочитать активную базу и вывести отчёты по обоим способам чанкинга.
go run ./week-05 index -inspect

# Просмотреть конкретный build/chunk; стратегию выбрать fixed или structural.
go run ./week-05 index -inspect -strategy structural -build BUILD_ID -chunk CHUNK_ID

# Посмотреть ближайшие пять чанков для запроса (поиск делает embedding запроса через Ollama).
go run ./week-05 index -inspect -strategy structural -search 'EU/t для perfect overclock' -k 5
```

`-inspect` открывает базу только для чтения, печатает сводку и inspection reports с чанками/разделами, статистикой источников и предупреждениями для стратегий `fixed` и `structural`. `-chunk` показывает полный исходный текст и ссылку для одного chunk ID. При `-search` fingerprint установленной Ollama-модели сверяется с fingerprint активного build.

При загрузке снимка программа пересчитывает SHA-256 каждого документа по фактическому тексту и сверяет с объявленным hash, затем проверяет ID снимка по документам и их хешам. Несовпадающий hash отклоняется; правка текста требует согласованного пересчёта метаданных.

Чтобы проверить другой snapshot или настройки, создайте отдельную временную базу; команда `index` активирует новый build в переданной базе, поэтому не направляйте эксперимент на рабочую БД:

```sh
go run ./week-05 index \
  -snapshot week-05/corpus/gtnh-20261004.json \
  -db week-05/rag-temporary.db -size 400 -overlap 80
```

Имя `rag-temporary.db` попадает под точное правило игнорирования SQLite-баз недели 5. Не удаляйте и не заменяйте активную `week-05/rag.db` ради эксперимента.

## 3. RAG, retrieval и оценка (дни 22–24)
### День 22 — первый RAG и сравнение

Контрольные сравнения — часть работы с первой RAG-линией и её сравнением с альтернативами: пять пар (`baseline-rag`, `fixed-structural`, `rag-filtered`, `filtered-rewritten`, `rag-grounded`) запускаются на каждом вопросе.

Стандартная пара retrieval-параметров чата — до **10** кандидатов и не более **3** фрагментов в контексте. Режимы ответа: `rag` использует найденные фрагменты; `filtered` применяет порог сходства; `rewritten-filtered` сначала переписывает поисковый запрос, затем фильтрует результаты; `grounded` требует обосновывать ответ доступным контекстом и обрабатывать недостаточность контекста. В фильтруемых режимах используется косинусное сходство.

### День 23 — фильтрация и переписывание

Файл `calibration.json` фиксирует узкую калибровку порога **0.60** для одного snapshot, fingerprint embeddings, structural-стратегии и шести размеченных примеров. Это не универсальный порог и не доказательство поддержки каждого факта: контекст из трёх фрагментов может отсечь релевантный результат ниже по рангу. Проверяйте конкретные фрагменты и ограничения источника.

Важно: `0.60` — настройка стандартного чата (`-threshold 0.60` и файл калибровки). `evaluate` по умолчанию использует `-threshold 0.25` и пометку `uncalibrated`; чтобы запустить контрольные сравнения с узким калиброванным профилем, передайте `-candidate-k 10 -context-k 3 -threshold 0.60 -calibration week-05/calibration.json -strategy structural`. Область калибровки всё равно ограничена указанными примерами и fingerprint.

Контрольный запуск выполняет пять пар (`baseline-rag`, `fixed-structural`, `rag-filtered`, `filtered-rewritten`, `rag-grounded`) на каждом вопросе из набора. При стандартном наборе это **50 сравнений / 100 обращений по линиям**. Команда ниже записывает JSON и Markdown в `week-05/evaluations/`:
```sh
go run ./week-05 evaluate \
  -provider deepseek \
  -questions week-05/questions.json \
  -candidate-k 10 -context-k 3 -threshold 0.60 \
  -calibration week-05/calibration.json -strategy structural \
  -interval 1s -temperature 0 -max-tokens 2048 \
  -out week-05/evaluations
```

Без `-provider` выбран Groq; перед запуском нужен соответствующий ключ окружения. `-interval 1s` задаёт паузу между последовательными обращениями и сравнениями, чтобы снизить частоту запросов. Отдельный ручной smoke-вопрос запускается так:

```sh
go run ./week-05 evaluate -provider deepseek \
  -question 'What does this corpus say about the requested GT:NH topic?' \
  -out week-05/evaluations
```

Просмотр ранее сохранённого сравнения не вызывает модели:

```sh
go run ./week-05 evaluate -run RUN_ID
```

`RUN_ID` — сохранённый ID результата в указанной БД. Отчёты включают наблюдения/метрики и настройки провайдера, retrieval и fingerprint, но не являются сами по себе доказательством ручной семантической оценки.

### День 24 — цитаты и отказ

Ответ в grounded-режиме должен содержать хотя бы одну цитату. Каждая цитата должна ссылаться на chunk, действительно переданный в текущий контекст, а её quote должна быть точной подстрокой текста этого chunk; источник и permalink берутся из сохранённых данных, а не доверяются модели. При `insufficient_context` ответ не может содержать цитат и отображается как отказ по недостаточности корпуса. Эти проверки подтверждают provenance и точность цитируемого фрагмента, но сами по себе не доказывают семантическую поддержку каждого утверждения.


## 4. Чат и парные режимы (день 25)

Обычный чат создаёт постоянную пару grounded-линий: первая без task memory, вторая с task memory.

```sh
go run ./week-05 chat -provider deepseek
```

Пара `grounded-memory` сравнивает grounded-ответы без task memory и с ней; `grounded-no-memory` отключает task memory в обеих линиях. `fixed-structural` сравнивает два вида чанкинга. Пары `baseline-rag`, `rag-filtered`, `filtered-rewritten`, `rag-grounded` требуют `-experiment`: такие эксперименты изолированы и не записывают долговременную историю. `-raw-turns` задаёт максимальное окно недавней истории.

В старых сессиях может отсутствовать достоверное значение `raw-turns`. Такие записи `ListSessions` может показать с неизвестным окном; загрузка сессии/добавление продолжения отклоняется с требованием миграции, потому что размер окна истории нельзя безопасно восстановить. Для продолжения начните новую сессию, а не угадывайте старое значение. Сессии без обязательной provider/endpoint provenance также нельзя возобновить с придуманными настройками — используйте новую сессию.

При `chat -session SESSION_ID` сохранённые raw-history window и provider/endpoint/model, sampling и retrieval-настройки восстанавливаются из самой сессии. Явное указание конфигурационного параметра создаёт новую чистую сессию, а не меняет старый диалог: это относится к `-raw-turns`, `-provider`, `-endpoint`, `-pair`, `-strategy`, `-candidate-k`, `-context-k`, `-threshold`, `-calibration`, `-main-model`, `-aux-model`, `-temperature` и `-max-tokens`.

```sh
go run ./week-05 chat -experiment -pair rag-filtered -provider deepseek
```

Для обычной сессии её ID показан в интерфейсе; явно возобновить её можно так:

```sh
go run ./week-05 chat -session SESSION_ID
```

### Сценарии с checkpoint и resume

Два утверждённых сценария (`progression`, `ore-processing`) состоят из 12 ходов каждый. Первый запуск создаёт сессию и останавливается на checkpoint после 10 ходов. Скопируйте `SESSION_ID` из строк `SCENARIO_TURN_COMMITTED`/`SCENARIO_CHECKPOINT` или из JSON-отчёта в `week-05/scenario-reports/`; затем возобновите ту же сессию до хода 12:

```sh
# Создать сессию и пройти ходы 1–10.
go run ./week-05 evaluate -scenario progression \
  -provider deepseek -until 10 -interval 1s \
  -temperature 0 -max-tokens 2048

# Возобновить эту сессию и пройти ходы 11–12.
go run ./week-05 evaluate -scenario progression \
  -session SESSION_ID -until 12 -interval 1s \
  -temperature 0 -max-tokens 2048
```

Для второго набора замените `progression` на `ore-processing` и создайте для него отдельный checkpoint-сеанс. Resume восстанавливает сохранённые provider/endpoint/model, generation и retrieval-настройки и продолжает историю сессии; явно заданные параметры генерации должны совпадать с сохранёнными. `-interval 1s` задаётся заново при каждом вызове: он делает паузу между последовательными вызовами линий и ходами, но не меняет конфигурацию диалога. Не передавайте `-raw-turns` на resume, если нет необходимости проверять совпадение с сохранённым окном.

В обоих сценариях, как и в обычной паре `grounded-memory`, task memory находится во **второй** grounded-линии; первая использует только ограниченную raw history.

## Результаты и ограничения

### Проверенные сохранённые результаты

Строгий control run завершён: **50 сравнений / 100 линий**, snapshot `snapshot-ec91e5a8c85c8f5a8633844d7c58d8f4`. Доступны [JSON](evaluations/deepseek-final-strict-diagnostic/evaluation-20261004T214200.834406000Z.json), [Markdown](evaluations/deepseek-final-strict-diagnostic/evaluation-20261004T214200.834406000Z.md) и полный [agent-authored semantic review](evaluations/deepseek-final-strict-diagnostic/full-semantic-review.json). Review проверяет все 50 сравнений и 100 ответов; это automated QA/agent review, не человеческая проверка.

Семантическая оценка показывает заметное улучшение grounded RAG против no-RAG на фактах, подтверждённых корпусом: no-RAG галлюцинирует или ошибается по q01, q02, q03 и q05–q08, тогда как RAG-ответы в основном цитируют корректные источники. Но это не универсальное превосходство. Все варианты ответа по q05 упускают caveat, что перечислены базовые, а не лучшие полные маршруты. В `filtered-rewritten` есть регрессии: неправильный отказ по q06 и неполный отказ по q08, несмотря на наличие подтверждений. В fixed/structural q04 один ответ частичный: он не сообщает конкретное misrouting при переполнении. См. полный review для разбора по вопросам/линиям.

Оба strict-сценария завершены: по 12 ходов, с рестартом после 10. Сохранены [progression JSON](scenario-reports/final-strict/scenario-progression-20261004T214412.361800000Z.json) и [Markdown](scenario-reports/final-strict/scenario-progression-20261004T214412.361800000Z.md), [ore-processing JSON](scenario-reports/final-strict/scenario-ore-processing-20261004T214606.714306000Z.json) и [Markdown](scenario-reports/final-strict/scenario-ore-processing-20261004T214606.714306000Z.md). [Полный сценарный review](scenario-reports/final-strict/semantic-review.json) — agent-authored, не human review. В progression общая цель Moon trip теряется в ходе сторонних вопросов (5–9), а turn 4 оставляет устаревший LV в цели после уточнения MV. В ore-processing memory лучше накапливает ограничения и поправки пользователя, но важные Rare Earth overflow/mitigation и replace-machine источники не попадают в контекст на нескольких ходах; из-за этого модель отказывается от некоторых вопросов, хотя они помечены как разрешимые по корпусу. Дополнительные недостатки: неподкреплённое объяснение power load в turn 1, неполное решение вопроса про переполнение в turn 12. Память сохраняет ряд целей и ограничений, но не гарантирует постоянное удержание родительской цели и не компенсирует retrieval-пробелы.
