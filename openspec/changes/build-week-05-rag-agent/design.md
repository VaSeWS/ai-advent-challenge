## Context

Мотивация и capability boundaries — в `proposal.md`. В репозитории уже есть Bubble Tea v2, Bubbles v2 и Lip Gloss v2. `week-04/agent/app.go` содержит textarea, viewport, resize и статус, но его `app` напрямую связан с `Store`, `Agent`, `CommandService` и MCP; `NewApp` делегирует в `NewAppWithMCP`. Это не импортируемая UI-библиотека: программа является `package main`.

`week-04/agent/llm.go` использует stdlib HTTP для OpenAI-compatible Chat Completions, но текущий контракт включает tool calls и не задаёт strict JSON Schema. Новый агент не переносит этот домен. Существующий SQLite-драйвер — `modernc.org/sqlite`; официальная интеграция sqlite-vec предлагает другой Go-драйвер. Старые программы остаются без изменений.

В локальном Ollama установлен `nomic-embed-text`; реальный запрос для документа и вопроса вернул два вектора по 768 конечных чисел. Retrieval quality ещё не измерялось. GT:NH wiki предоставляет MediaWiki API, revision IDs и CC BY-SA 4.0; отдельные статьи предупреждают об устаревании и отсылают за полными рецептами к NEI/Quest Book.

## Goals / Non-Goals

**Goals:**

- Сделать сравнения воспроизводимыми: снимок корпуса, fingerprint embedding-модели, параметры chunking/retrieval и модель ответа фиксируются вместе с результатом.
- Разделить индекс, поисковый эксперимент и чат; сохранять данные локально без отдельного векторного сервера.
- Показать retrieved evidence и отказ как полноценный результат, а не скрыть неудачные вопросы.
- Ограничить заимствование из прежнего TUI компонентами и узкими паттернами ввода/прокрутки/layout.

**Non-Goals:**

- Полная база игровых рецептов, чтение NEI/Quest Book, выполнение игровых действий или гарантия актуальности wiki для любой версии модпака.
- MCP, долговременные профили, lifecycle/invariants задач, ветвление, пять стратегий контекста прежнего агента или общая библиотека для всех недель.
- Автоматический fallback, retry/backoff, самостоятельное обновление снимка во время чата, отдельный reranker, автоматический LLM-судья качества.
- Streaming structured answers: первый вариант показывает статус и готовый ответ каждой панели.

## Decisions

### 1. Одна программа и локальные границы

`week-05` — один `package main` в существующем Go-модуле. Логические части: corpus ingestion, chunking, embeddings, store, retrieval, answer generation, chat state, evaluation и TUI. Разделение файлов не создаёт framework или избыточные интерфейсы; injectable HTTP endpoint/client нужен только на внешней границе.

CLI предоставляет явные действия `corpus`, `index`, `evaluate` и `chat`; TUI чата имеет экраны сравнения, найденного контекста и task state. Индексацию и корпус не пересоздаём автоматически при запуске чата. Defaults моделей и адресов можно переопределить флагами; ключ Groq читается только из environment.

Альтернатива — пять day-пакетов или копия `week-04/agent`: отвергнута из-за дублирования и ненужной связи с MCP/lifecycle. Общую UI-библиотеку заранее не выделяем. Английские UI/prompts согласованы с пользователем; планирование и объяснения в README — на русском.

### 2. Датированный снимок официальной wiki

Получаем страницы через `https://wiki.gtnewhorizons.com/w/api.php` с явным списком titles. Начальный пул: Tier, LV–UXV guides, Electricity, Power Generation, Ore Processing Concepts, Ore Processing, Rockets, Planets. Фактические canonical titles, redirects и revision IDs разрешаются API, а не угадываются.

Сохраняем manifest: canonical title, page ID, revision ID/timestamp, retrieval timestamp, permalink с `oldid`, content hash, лицензия и attribution URL. Извлекаем содержимое именно сохранённой ревизии в структурированный текст: заголовки, абзацы, списки, таблицы и блоки кода. Удаляем навигацию/служебные блоки, но сохраняем предупреждения об устаревании. Рецепты в изображениях не объявляем извлечёнными фактами. Предпочтение — revision-pinned rendered HTML; для надёжного парсинга допустим `golang.org/x/net/html`, а не regex по произвольному HTML.

Достаточный объём: минимум 15 000 английских слов полезного текста до overlap, при явно принятой оценке 500 слов/страницу, то есть 30 page-equivalents. Количество веб-страниц само по себе не считается доказательством объёма. Если начальный список меньше, расширяем его связанными wiki-страницами и записываем окончательный manifest. Для воспроизведения сохраняем нормализованный снимок и manifest с атрибуцией; большие исходные ответы API и сгенерированная БД не обязательны для коммита.

Новый снимок создаётся явной командой, старый не перезаписывается незаметно. Wiki revision timestamp и версия модпака — разные метаданные; версия указывается только там, где она явно подтверждена источником. Отсутствующая страница, revision mismatch или пустой текст — ошибка получения, а не fake fallback.

### 3. Две стратегии на одном тексте

Начальные параметры: fixed-size — 400 слов и overlap 80 слов; structural — границы headings/sections с целевым размером до 400 слов, с разбиением длинных разделов на подчанки и overlap только внутри раздела. Это настраиваемые исходные значения, а не утверждение об оптимальности.

Обе стратегии используют один нормализованный снимок. Fixed-size не смешивает документы; если он пересекает heading boundary, метаданные перечисляют покрытые section paths. Structural не смешивает несвязанные разделы. Детерминированный `chunk_id` учитывает snapshot, page/revision, strategy, параметры и позицию. Сохраняем source, title, section paths, порядковый номер, текст и смещения в нормализованном документе.

Сравнение дня 21 включает число/размеры чанков, overlap overhead, визуальную целостность примеров, наличие ожидаемого источника в top-K. Оптимальную стратегию выбираем после одинакового контрольного набора, не по одному количеству чанков.

### 4. Ollama и совместимость индекса

Default: `nomic-embed-text` через `http://localhost:11434/api/embed`, исходная размерность 768. Документы получают `search_document:`, вопросы — `search_query:`. Перед работой читаем metadata установленной модели; сохраняем полное имя, digest, размерность и версию подготовки входа. `truncate: false`; batch входы соответствуют исходному порядку. При несовпадении количества векторов, размерности, нечисловых/не finite значениях или нулевом векторе индексация прекращается.

Fingerprint проверяется перед retrieval. Смена модели, digest, размерности или подготовки текста требует явной переиндексации, даже если число измерений осталось тем же. Не скачиваем модель автоматически и не заменяем локальную модель облачной при ошибке.

Альтернативы: EmbeddingGemma — мультиязычный кандидат, но сейчас потребовала бы новую загрузку без доказанной необходимости для английского корпуса; OpenAI embeddings отвергнуты пользователем в пользу локального Ollama.

### 5. SQLite + sqlite-vec без CGO

Используем официальные `github.com/asg017/sqlite-vec-go-bindings/ncruces` и `github.com/ncruces/go-sqlite3` с WASM SQLite, через его `database/sql` интеграцию. Не загружаем это расширение в `modernc.org/sqlite` и не меняем драйвер старых программ. Зависимости пинятся в корневом модуле. Первое acceptance evidence интеграции — реальный `vec_version()`, запись вектора и KNN-запрос, а не только сборка.

Обычные таблицы хранят snapshots, documents, sections, index builds, chunks, comparison runs/results, sessions, lane messages, task state. Вектора находятся в `vec0` с `distance_metric=cosine`, связаны с chunk rows по ID. Fixed и structural поиски изолируются strategy/index-build partition либо отдельными vec0-таблицами: нельзя взять общий top-K и лишь после этого удалить чанки другой стратегии. Зафиксированная размерность одинакова для обоих индексов.

Индекс строится отдельно от активного build; active marker меняется транзакционно только после готовности документов, чанков и всех эмбеддингов. Ошибка не подменяет рабочий индекс частичным. Старые runs сохраняют ссылку на использованный snapshot/build. Нет автоматических инкрементальных миграций эмбеддингов. Сгенерированные `*.db`, WAL/SHM и записи видео игнорируются адресно для `week-05`.

Альтернативы: JSON не даёт SQL-поиска; точный поиск в Go заменён выбранным пользователем sqlite-vec; CGO добавляет toolchain; Qdrant/FAISS не нужны для масштаба корпуса. Не обещаем ANN или конкретную latency без измерения.

### 6. Режимы retrieval и честное сравнение

Режимы: `no-rag`, `rag`, `filtered`, `rewritten-filtered`, `grounded`. Для каждого выбирается fixed либо structural index. Начальные `candidate_k=10`, `context_k=5`; cosine distance меньше означает ближе, отображаемый similarity равен `1 - distance`. Порог подбирается на релевантных и нерелевантных примерах контрольного набора и записывается в настройки/run. До калибровки порог помечается некалиброванным, а качество не объявляется улучшенным.

- `no-rag`: без retrieval и без скрытой передачи документов/памяти другой панели.
- `rag`: retrieval исходного вопроса и top context-K без threshold/rewrite.
- `filtered`: те же кандидаты, отсечение по порогу, затем top context-K.
- `rewritten-filtered`: GPT-OSS 20B выдаёт самостоятельную search query без ответа на вопрос, затем embeddings/retrieval/filter. Исходный вопрос всегда остаётся основным пользовательским запросом.
- `grounded`: filtered retrieval с обязательной проверкой источников/цитат и отказом; rewrite — отдельный явно отображаемый переключатель.

Для изоляции эффекта предоставляем пары no-rag/rag, rag/filtered, filtered/rewritten-filtered, rag/grounded, fixed/structural при одинаковом режиме. Не сравниваем разные модели как доказательство пользы RAG. В одиночном эксперименте история отсутствует. Настройки main-модели и бюджета ответа одинаковы; prompts отличаются только выбранным механизмом. Baseline не получает правило «отвечать только по предоставленным чанкам», иначе отсутствие чанков даст искусственный отказ вместо честного ответа без RAG.

Сохраняем original/rewrite query, mode/strategy, model, threshold, K, найденные кандидаты и distances, оставшийся контекст, ответ и время. Никакого автоматического web search в модельном запросе. Два HTTP-запроса main-модели выполняются независимо после подготовки контекста, без блокирования TUI. Отдельный reranker не входит в scope: фильтр уже выполняет второй этап дня 23.

### 7. Structured answers и fail-fast

Groq defaults: `openai/gpt-oss-120b` для обоих ответов и `openai/gpt-oss-20b` для rewrite/task state. Stdlib HTTP + JSON, ограниченные timeout и response size, без retry/backoff. Ключ только `os.Getenv("GROQ_API_KEY")`, не в БД, логах или экспортированных запросах. Точные generation settings записываются вместе с run. Автоматического переключения на DeepSeek нет; это отдельная будущая потребность, не обязательный перенос provider framework прошлой недели.

Structured outputs используют строгую схему. Общая форма ответа содержит answer и citations; citation содержит chunk ID и дословную quote. Для baseline citations могут быть пустыми; renderer явно пишет `Sources: not used`. Для grounded непустой содержательный ответ требует хотя бы одной допустимой цитаты. Source/section/revision/permalink renderer берёт из БД, а не доверяет URL, придуманному моделью.

Код проверяет принадлежность cited chunk текущему контексту и точное вхождение quote в его нормализованный текст. Отчёт отдельно различает наличие источников, точность цитат и смысловую поддержку ответа. Формальная проверка цитаты не доказывает истинность или полноту ответа. Wiki-контекст — недоверенные данные, его инструкции не меняют системные правила.

Если после фильтра не осталось контекста, программа без main LLM call выводит `I don't know based on this corpus`, просьбу уточнить и `Sources: none — insufficient context`. Если чанки есть, но не содержат ответа, модель возвращает structured insufficient-context status; он отображается так же без выдуманных цитат. Кандидаты для инспекции не выдаются за подтверждающие источники отказа.

Некорректный JSON, unknown chunk, fabricated quote, timeout или HTTP failure — техническая ошибка, не «не знаю». Не исправляем автоматически и не генерируем повторно. Активная операция отменяется, терминал восстанавливается, программа завершает работу с понятным stderr и exit 1. В сравнении можно показать уже готовую панель как временный результат, но завершённая пара не сохраняется при ошибке второй панели.

### 8. TUI и сравниваемые диалоги

Общий textarea; две lane-модели со своим mode, strategy, status, viewport и результатом. Tab переключает фокус; PgUp/PgDn и wheel прокручивают выбранную панель; resize пересчитывает размеры без потери данных. При ширине меньше 120 колонок панели расположены вертикально. Английские названия режимов, источники и цитаты доступны без обрезания до невосстановимого фрагмента. Источник/контекст можно открыть в отдельном viewport. Structured output не стримится: показываем статус, затем полный результат.

Пока сравнение выполняется, новый submit блокируется. Ответы tagged по run/lane, чтобы позднее завершение не попало в другой результат. Выбор новой пары создаёт новую comparison session; прежние истории не переименовываются и не смешиваются. Пользователь может открыть сохранённую сессию или начать чистую.

В день 25 default — grounded chat, источники обязательны для содержательных ответов. Для демонстрации памяти можно сравнить grounded chat без task state и с task state; retrieval и политика источников одинаковы.

### 9. История и task state

Persisted messages разделены по session/lane. Все пользовательские сообщения сохраняются, assistant messages каждой панели доступны только своей панели. Prompt получает bounded raw history: начально шесть последних turn; task state не заменяет raw запись. Для продолжения модель rewrite использует историю своей панели и, если включён, её task state, чтобы разрешить ссылки вроде «а теперь следующий tier». В чат-режиме context resolution используется в обеих панелях сравнения памяти и не смешивается с одиночным rewrite-экспериментом дня 23.

Task state — goal, clarifications, constraints, terms. GPT-OSS 20B извлекает полное следующее состояние из прежнего state и явных пользовательских реплик; при конфликте последнее пользовательское уточнение заменяет старое. Недоказанные предположения assistant не становятся пользовательскими ограничениями. State участвует в search-query context и main prompt, показывается отдельным экраном. Current user message имеет приоритет над старым state/history.

При успешном turn messages, оба lane results и обновления state записываются одной транзакцией; при невалидном state или ошибке одной панели успешный turn не коммитится частично. Отказ из-за отсутствия контекста — успешный результат и может сохранить новые пользовательские ограничения. Новая сессия очищает goal/state; перезапуск восстанавливает выбранную сессию. Нет task lifecycle, автоматических планов или профилей.

### 10. Оценка и записи по дням

Конкретные десять контрольных вопросов определяются позднее, после проверки снимка. Формат записи: ID, question, expected facts, expected source/section IDs или явное отсутствие источника, признак достаточности корпуса. Включить узкие факты, исключения, вопросы по нескольким разделам и случаи без ответа; отдельно можно иметь calibration examples, не заменяющие контрольные десять.

На одном наборе сравниваем две стратегии chunking, no-rag/rag, rag/filtered и filtered/rewritten-filtered. Для каждого ответа сохраняем фактический результат; ручная рубрика проверяет ожидаемые факты, retrieval expected-source hit, источники, цитаты и смысловую поддержку. Отчёт не подменяет реальную оценку неизменяемым выводом «RAG лучше» и не требует улучшения на каждом вопросе.

День 24 проверяет все десять: у содержательных grounded-ответов источники и цитаты, у отказов явная причина и отсутствие fabricated citations. День 25 — два сценария по 10–15 пользовательских turn (каждый turn включает ответ), темы progression и ore processing. Конкретные реплики пользователь отложил; сценарии проверяют накопление/исправление ограничений, сохранение цели и источников, включая продолжение после перезапуска.

Пять видеозаписей либо пять явно выделенных сегментов покрывают результаты каждого дня; в repo лежат воспроизводимые demo scripts и инструкция, сами видео — вне Git. TUI smoke проводится на реальном терминальном surface; для записи применяется отдельный recording workflow при реализации.

## Risks / Trade-offs

- [RAG может не улучшить знакомые модели факты] → оценивать узкие вопросы и корректность evidence; фиксировать действительные результаты без подбора заведомо слабого baseline.
- [Wiki устарела или неполна] → revision-pinned snapshot, сохранение warnings, явные corpus boundaries и отказ вместо дополнения «из игры».
- [HTML таблицы/изображения теряют смысл] → сохранять связи заголовков и ячеек, вручную проверить несколько таблиц; вопросы только по действительно извлечённым данным.
- [Ollama tag изменяет веса] → digest fingerprint и отказ от поиска несовместимым индексом.
- [WASM-driver/sqlite-vec version mismatch] → пиновать зависимости и первым проверить vec_version, persisted KNN и cosine ordering. Совместимость пока не доказана запуском.
- [Порог удаляет правильный фрагмент, rewrite меняет смысл] → отображать все кандидаты и rewritten query, оценивать механизмы отдельными парами.
- [Грамматически корректная citation не поддерживает вывод] → разделить deterministic provenance validation и ручную semantic evaluation.
- [Groq quotas или schema не поддержаны аккаунтом] → проверить реальный main/auxiliary вызов до полной демонстрации; fail-fast, не подменять модель автоматически.
- [Два ответа и память увеличивают latency/cost] → локальные embeddings, малый вспомогательный model и ограниченный контекст; измерять фактическое время.
- [Retrieved текст уходит во внешний API] → явно указать это в UI/README; локальные embeddings не означают полностью локальный чат.

## Migration Plan

Добавление изолировано в `week-05`; старые БД и команды не мигрируются. В реализации сначала подтвердить WASM/sqlite-vec и Ollama, затем подготовить снимок, оба индекса и режимы по дням. Корневой модуль и README обновляются только при apply. Для rollback достаточно запускать прежние программы; новую БД не передавать старым агентам. Пересборка индекса выполняется явной командой и не удаляет активный build при неудаче.
