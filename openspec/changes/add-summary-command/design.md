## Context

См. proposal.md — Why. `store.Summary(branchID)` уже возвращает сохранённое резюме ветки вместе с watermark и отдаёт `nil, nil`, когда резюме ещё нет. `/facts` в `CommandService` устроен ровно так же: читает store, форматирует, возвращает `CommandResult.Status`.

## Goals / Non-Goals

**Goals:**

- Сделать видимым то, что уже хранится: содержимое резюме и границу, по которую оно построено.

**Non-Goals:**

- Принудительное построение или пересборка резюме командой: резюме остаётся ленивым, его строит следующий turn в режиме `summary`.
- Редактирование или удаление резюме из TUI.

## Decisions

**Симметрия с `/facts`.** Команда читает store, не трогает Agent и не вызывает LLM, поэтому работает в любом режиме и не блокируется во время API-вызова иначе, чем остальные читающие команды. Альтернатива — показывать резюме в статусной строке после каждого turn — засоряла бы статус многострочным текстом.

**Watermark в заголовке.** `summary (through message <id>)` показывает, какая часть истории уже свёрнута; без него невозможно отличить свежее резюме от отставшего.

## Risks / Trade-offs

- [Длинное резюме занимает экран] → вывод идёт в transcript, который уже прокручивается `PgUp`/`PgDn`; отдельного ограничения не вводится.
