# День 26 — Qwen локально на Apple Silicon

## Задание и профиль

Запустить локальную языковую модель через CLI или HTTP API и показать три запроса возрастающей сложности: короткий вопрос, оценка памяти и алгоритмическая задача. Подготовить видео с настоящим TUI-агентом из `week-04/agent` и локальным HTTP API MLX.

Текущий runtime: `mlx-community/Qwen3.5-4B-4bit`, revision `0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`. Ранее измеренный запуск Qwen3.8-27B-4bit теперь является только историческим. Его арифметический минимум веса сохранён: `27 × 10⁹ × 4 / 8 = 13.5 × 10⁹` байт (13.5 десятичных ГБ); это не измерение памяти процесса и не характеристика выбранной 4B модели. KV-cache, вычисления и runtime требуют дополнительной памяти. Счётчик токенов агента — оценка по длине текста, не точный Qwen tokenizer.

Установите окружение и веса из корня репозитория:

```sh
./week-06/day-26/runtime/setup.sh
```

В отдельном терминале запустите сервер:

```sh
DAY26_KV_SIZE=40960 ./week-06/day-26/runtime/serve.sh
```

Сервер слушает только `127.0.0.1:8080`; Chat Completions endpoint — `http://127.0.0.1:8080/v1/chat/completions`, список моделей — `http://127.0.0.1:8080/v1/models`. Thinking включён. `DAY26_KV_SIZE` задаёт реальный MLX `--max-kv-size` для подготовленного prompt и зарезервированного ответа; default `16384`, положительное целое. Профиль демо `40960` — лимит запуска, не нативная ёмкость модели. Реальный main + memory прогон выбранного snapshot и native `memory_update` schema прошли clean dry-run; визуальная запись — отдельный гейт.

Запустите TUI с отдельной новой SQLite-базой:

```sh
go run ./week-04/agent \
  -provider local \
  -endpoint http://127.0.0.1:8080/v1/chat/completions \
  -model "$HOME/.cache/huggingface/hub/models--mlx-community--Qwen3.5-4B-4bit/snapshots/0e7ffd5c629ef7719d4cbc04069232580bfa9d9c" \
  -db /путь/к/новой-базе.sqlite \
  -context-window 40960 \
  -max-tokens 38912 \
  -thinking-budget 32768 \
  -aux-max-tokens 4096 \
  -request-timeout 90m
```

Параметры: context/KV `40960`, основной лимит `38912`, thinking budget `32768` внутри основного лимита, auxiliary `4096`, timeout `90m` на запрос. Разница `2048` (`38912 + 2048 = 40960`) оставлена для prompt; это не обещает, что любой запрос поместится. MLX проверяет точную сумму подготовленного prompt и зарезервированного ответа. Большой KV/context требует дополнительной памяти.

Обычное локальное извлечение памяти использует `enable_thinking=false` и native `json_schema` с именем `memory_update`; main остаётся с thinking on. Schema описывает существующий typed memory contract, допускает `{}` при отсутствии обновления и не заменяет финальную проверку parser. Лимиты и timeout не сокращались.

## Проверенное выполнение
В реальном прогоне Qwen3.5-4B основной ответ и штатное извлечение памяти успешно сохранены: clone содержит четыре чата, восемь сообщений и восемь API-вызовов — шесть исторических 27B и два новых 4B. В первом функциональном прогоне основной запрос завершился за `28.99` с, memory — за `6.24` с; оба с `finish_reason=stop`. Его внешняя очистка tmux завершилась ошибкой; этот прогон сохранён отдельно. Позднее стандартный history+LIVE dry-run v4 завершился с exit 0. Самый новый стандартный dry-run v3 также завершился с exit 0: четыре чата, восемь сообщений, восемь API-вызовов и неизменность исходной базы/sidecars подтверждены. Совместная запись v3 завершилась с exit 0 за `86.9` с; это выполнение задания, не benchmark выбора модели.

Исторические измерения и oracle proof в этом разделе относятся к прежнему Qwen3.8-27B-4bit snapshot `10c35caafbb80f7dc6a7a432cdd11af10a6d4818`; они не подтверждают работу нового 4B runtime.

В фактическом прогоне настоящего TUI три независимых исходных запроса завершились за `2246.17` с: три основных и три штатных memory-вызова, все HTTP 200 и `finish_reason=stop`. Каждая пара вопрос/ответ сохранена в отдельном чате свежей SQLite-базы; память не отключалась. Сложный основной запрос занял `1793.629` с и сгенерировал `17714` completion-токенов суммарно (это не подсчёт thinking-токенов). Функция Go из ответа прошла неизменённый независимый оракул: 7 контрольных/скрытых примеров и 5460 исчерпывающих проверок с проверкой неизменности входа. Это доказательство одного успешного прогона, не причинного эффекта отдельной настройки и не гарантии будущей стабильности.

Отдельная проверка границы с prompt простого запроса (126 токенов) приняла `126 + 40834 = 40960` и отклонила `126 + 40835 = 40961` с HTTP 400 до генерации. Эти диагностические запросы не входят в шесть вызовов TUI. Текстовые снимки не заменяют визуальную проверку.

## Демонстрационный сценарий

Обычный `video/demo.sh` создаёт свежую SQLite-базу и запускает три независимых запроса из `prompts.json`, дожидаясь сохранения каждого ответа. Перед вопросами 2 и 3 создаётся отдельный чат. Thinking и обычное извлечение памяти остаются включёнными; MCP-серверы не требуются, ошибки main- или memory-вызова не обходятся. `DAY26_ENDPOINT` задаёт полный Chat Completions URL; default `http://127.0.0.1:8080/v1/chat/completions`. Для прокси можно указать, например, `http://127.0.0.1:8081/v1/chat/completions`; проверка `/v1/models` остаётся на локальном сервере по умолчанию.

Оставьте `DAY26_DB` незаданной для отдельной временной базы. Если задаёте её, используйте новый путь, которого ещё нет, или пустой файл. База пользователя не удаляется. База и её `-wal`/`-shm` должны разрешаться вне `DEMO_ARTIFACT_DIR`, включая проверки symlink/alias. Каталог `DEMO_ARTIFACT_DIR` должен быть новым: скрипт создаёт его эксклюзивно и отказывается перезаписывать существующие артефакты. Пример обычного режима:

```sh
DAY26_DB="$PWD/day26-demo.sqlite" \
DEMO_ARTIFACT_DIR="$PWD/day26-artifacts" \
./week-06/day-26/video/demo.sh
```

Для утверждённой совместной демонстрации дней 26–27 предусмотрен `DAY26_HISTORY_DB` с исходной SQLite трёх успешных запросов. Сценарий проверяет исходные prompts, три ответа, шесть сообщений и шесть main/memory API-вызовов, отсутствие MCP, затем байтово копирует базу и существующие `-wal`/`-shm` в эксклюзивный staging-каталог `0700`; только staged-копия открывается SQLite для проверки и backup в clone `0600`. Исходный DB и sidecars проверяются на обычные файлы без symlink, стабильную identity, присутствие/отсутствие и SHA-256 до/после копирования и после всего TUI LIVE сценария; source и sidecars должны находиться вне каталога артефактов. Непустой WAL копируется и учитывается SQLite на staging-копии, а не удаляется. `DAY26_HISTORY_DB` несовместим с `DAY26_DB`.

В режиме истории `/use 1`, `/use 2`, `/use 3` показывают прошлые ответы под подписью «История реального прогона». Затем новый чат `/new Day 26 — LIVE simple` отправляет исходный simple prompt реальной модели. Успешный clone содержит четыре чата, восемь сообщений (четыре ответа assistant) и восемь API-вызовов: шесть исторических и два новых (main + memory). `provenance.json` различает историю и LIVE turn; `day26.sqlite` — backup clone, не исходной базы. Пример с локальной acceptance-базой:

```sh
DAY26_HISTORY_DB="$PWD/.omp/task-execute/runs/week06-local-llm-20261011/evidence/day26-thinking32k-source-v8.sqlite" \
DEMO_ARTIFACT_DIR="$PWD/day26-history-live-artifacts" \
bash week-06/day-26/video/demo.sh
```

Оба режима сначала запрашивают `/v1/models` без генерации. LIVE-запрос использует обычные main- и memory-вызовы; timeout каждого — `90m`. Сценарий не делает retry и сам не записывает видео.

## Совместное видео 26–27 — опубликовано

Пользователь утвердил точный план пяти кадров v3. Стандартный dry-run v3 завершился с exit 0, подтвердив четыре чата, восемь сообщений, восемь API-вызовов и неизменность исходной базы/sidecars. Последняя стандартная запись v3 завершилась с exit 0; MP4 длится `86.9` с и прошёл независимую визуальную приёмку. Совместное видео опубликовано через локальный Yandex Disk MCP: https://yadi.sk/d/S-TbYMilKL3r2Q.

1. Показать выбранную Qwen3.5-4B-4bit и pinned revision `0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`; выполнить `curl -fsS http://127.0.0.1:8080/v1/models`.
2. `/use 1`: полный простой вопрос и исторический ответ Qwen3.8-27B; не представлять его как новую генерацию.
3. `/use 2`: исходный вопрос о весах 27B, расчёт `27e9 × 0,5 Б = 13,5e9 Б = 13,5 ГБ` и overhead; это не расход памяти 4B.
4. `/use 3`: полный исторический Go-ответ Qwen3.8-27B, инвариант двух указателей, `O(n)`/`O(1)`, неизменность входа и примеры 6/9; показать все читаемые страницы отдельными клавишами PageUp/PageDown.
5. Создать `/new Day 26 — LIVE simple` и отправить отдельным сообщением `Ответь по-русски ровно одним предложением: что такое локальная языковая модель?`; показать полный новый Qwen3.5-4B ответ с обычными main + memory вызовами.

Утверждение плана сохранено в `.omp/task-execute/runs/week06-local-llm-20261011/evidence/combined26-27-qwen35-plan-approved-20261013.json`. Runtime/provenance записи v3 находятся в `evidence/day26-27-final-record-20261014-v3/`; стандартный dry-run — в `day26-27-final-dryrun-20261014-v3/`. Первый failed take выявил унаследованный tmux-server TTY: теперь его stdio направлен в `/dev/null`. Второй take завершил приложение успешно, но был отклонён guard из-за изменившегося состояния окна. Перед чтением статуса driver теперь явно joined. Успешная запись подтверждает attachment, completion и сохранённые foreground/ownership guards; failed takes не публиковались.
