# Day 30 — private local chat service

This standalone, stdlib-only Go HTTP service has optional Telegram long polling. It provides ordinary conversation, **not RAG**. Its current pinned backend is `mlx-community/Qwen3.5-4B-4bit` revision `0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`; clients cannot choose another model or submit media, tools, backend headers, or arbitrary backend options.

## Prerequisites and manual startup

1. Start MLX-VLM 0.6.8 separately on `127.0.0.1:8080` with `--max-kv-size 16384`, thinking enabled, and the pinned Qwen3.5-4B snapshot from `main.go`: `mlx-community/Qwen3.5-4B-4bit@0e7ffd5c629ef7719d4cbc04069232580bfa9d9c`. For the default Hugging Face cache, run `MODEL="$HOME/.cache/huggingface/hub/models--mlx-community--Qwen3.5-4B-4bit/snapshots/0e7ffd5c629ef7719d4cbc04069232580bfa9d9c"; mlx_vlm.server --model "$MODEL" --host 127.0.0.1 --port 8080 --enable-thinking --max-kv-size 16384`. Do not expose the raw backend port to the LAN. The Go service checks backend health, loaded snapshot, and effective context cap before opening its listener.
2. Generate a fresh random service bearer token of at least 32 characters and provide it through `DAY30_SERVICE_TOKEN` using a private environment setup. Never put credentials in arguments, shell history, source, logs, or recordings. The program reads environment variables only; it does not load `.env` files.
3. From the repository root, start manually with `go run ./week-06/day-30`. By default it binds one discovered private IPv4 address at port 8090. If multiple addresses are found, choose with `-listen PRIVATE_IP:8090`. `-dev-loopback` is for explicit local development only. No launch agent or automatic startup is installed.
4. Telegram is optional and requires both existing `TELEGRAM_BOT_TOKEN` and configured private `TELEGRAM_CHAT_ID`; leave both unset to disable it. Before opening HTTP, the process refuses a configured webhook and waits for successful initial `getUpdates`. A competing poller or API error fails startup. It never deletes a webhook; polling is outbound only.
5. Stop with Ctrl-C or SIGTERM. Telegram history exists only in process memory and is lost on shutdown. Keep the Mac awake for service/polling availability.

HTTP is plain, unencrypted traffic: use only on a trusted private LAN; do not port-forward or expose it to public networks. `/health` and `/v1/limits` expose sanitized status/limits without the bearer token. Every `POST /v1/chat/completions` requires `Authorization: Bearer …` and accepts only typed text messages, optional `model: "local"`, and optional bounded `max_tokens`. Requests are limited to 64 KiB and 32 messages; each message is at most 8192 UTF-8 bytes. Default output cap is 1024 tokens, maximum 2048. Backend context cap 16384 is authoritative and rejects requests that do not fit prompt plus output; the service does not present a client-side token estimate as exact.

Only one backend generation is admitted at a time. Each has a service-owned finite 30-minute deadline. Per source IP, three chat requests per minute are allowed, with `Retry-After` on 429. The limiter uses `RemoteAddr`; forwarded headers are ignored.

The private chat API requests direct, non-thinking answers (`enable_thinking=false`) so its bounded output budget is used for final text; `/v1/limits` advertises the same mode. This is Qwen's documented [instruct/non-thinking mode](https://huggingface.co/Qwen/Qwen3.5-4B#instruct-or-non-thinking-mode), passed as the flat field supported by MLX-VLM 0.6.8. The backend can still start with `--enable-thinking`; this request-level choice does not change days 26–29. Output/body/history/rate limits and terminal-error checks remain unchanged. This mode is verified below as actual service acceptance, not a local model-selection benchmark or a claim about reasoning quality.

## Disconnect, completion, and recovery

MLX-VLM 0.6.8 records GPU-worker cancellation but does not acknowledge that generation stopped. Therefore disconnect or caller deadline does **not** cancel upstream work. The handler drains the one finite upstream SSE response under a service-owned 30-minute deadline, retaining exclusive admission and never issuing a replacement request. Completion requires a consistent nonempty completion ID, exactly one intended text choice, supported `finish_reason` (`stop` or `length`), no error SSE, and a genuine terminal `data: [DONE]`; `[DONE]` alone is insufficient. An abandoned response is never sent or committed. Admission reopens only after confirmed completion.

For `length`, the service preserves the generated text and the `length` result. Telegram delivers a nonempty capped answer and commits history only after every chunk is delivered. Confirmed completion with empty text releases admission but returns a sanitized failure and commits no history.

If upstream times out, transport/read or SSE decoding fails, identity is missing/conflicts, a backend error occurs, choice/finish reason is invalid or missing, or `[DONE]` is absent, the service cannot establish whether MLX is still generating. It fails closed and keeps admission unavailable; inspect MLX and restart this service only after independently confirming the backend is idle. Never clear the lock or restart MLX blindly. An MLX HTTP 400 is treated as a completed request/context rejection; other ambiguous backend failures retain the lock.

Bounded draining is not prompt cancellation and can occupy the caller's slot until MLX finishes or the 30-minute cap expires. Shutdown closes admission and waits for active handlers up to that cap plus a short grace period. Unexpected Telegram polling, local-service, or delivery failure also stops the service after bounded drain; there are no retries. After ambiguous backend failure, process restart still requires independent confirmation that MLX is idle. The Go-side deadline does not prove GPU work stopped.

Actual finite TCP disconnect/drain checks passed at two observer boundaries: first backend bytes and first decoded content/reasoning delta. In the current direct-answer wave, both cancellations occurred while generation was active; production handlers retained admission until terminal completion and drained in 149/150 ms. This is **not** proof of GPU prefill/decode phases or prompt cancellation. Exact GPU-phase classification and clock ordering remain unproven; the earlier thinking-mode wave is retained separately.

## Telegram behavior

Only the private chat whose ID exactly matches `TELEGRAM_CHAT_ID` is processed; other chats and groups are ignored before any local-model request or reply. `/start` gives help, `/reset` clears in-process conversation, and ordinary text uses the same authenticated local HTTP endpoint. The bot retains the system instruction and complete user/assistant pairs, prunes oldest pairs while preserving the current question, and fits every retained message within the API's 8192 UTF-8-byte limit. If the newest delivered answer alone exceeds that limit, its whole pair is dropped rather than truncating the delivered answer.

The private-chat allowlist is access control, not end-to-end encryption or local-only message handling. Telegram receives bot messages through its service; use non-sensitive prompts for acceptance and phone recordings. The Telegram-to-local-service HTTP client deliberately bypasses environment proxies so its bearer and conversation stay on the direct local hop. The external Telegram API client retains its normal outbound proxy behavior. This does not encrypt the plain HTTP LAN API.

Long answers are split on Unicode rune boundaries under Telegram's UTF-16-unit limit. If any chunk delivery fails, delivery stops and the turn is not committed; already delivered chunks cannot be recalled, and the sanitized fatal diagnostic reports delivered/total chunks. HTTP clients refuse redirects for generation, health, Telegram API, and Telegram-to-service requests, preventing private request bodies and bot credentials from being replayed to redirect destinations.

Telegram accepts nonempty `stop` and `length` terminal results. A capped `length` answer is preserved, not retried or discarded solely for reaching the output limit. Empty text and unsupported finish reasons fail. History is committed only after every message chunk has been delivered.
